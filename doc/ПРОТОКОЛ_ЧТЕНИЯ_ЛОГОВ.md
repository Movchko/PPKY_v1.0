# Протокол чтения журнала событий ППКУ v1

**Версия:** 2.0  
**Режим доступа:** только чтение (нет команд удаления, очистки или изменения лога)

Формат записи: [`event_log_catalog.json`](event_log_catalog.json), [`ЛОГЕР_СОБЫТИЙ.md`](ЛОГЕР_СОБЫТИЙ.md).

---

## 1. Область применения

| Канал | v2.0 | Примечание |
|-------|------|------------|
| **RS485 (UART4)** | **да** | основной проводной доступ ПО |
| **UART2 (ESP32 / Wi‑Fi)** | **да** | тот же протокол, отдельные типы BSU-кадров |
| **CAN-шина** | **нет** | зарезервировано на будущее (§8) |

**Ограничение транспорта RS/UART:** один кадр — **не более 256 байт** (включая заголовок и CRC).

**Инварианты выгрузки:**
1. Нумерация пакетов потока непрерывна (`pkt_num`: 0, 1, 2…).
2. Внутри кадра — **только целые события** (32 байта + метаданные); событие **никогда** не разбивается между двумя кадрами.
3. ПО может запросить «весь лог» — ППКУ сама нарезает поток кадрами ≤256 байт.

---

## 2. Кадр RS/UART (оболочка BSU)

Общий формат с CAN-мостом (`backend.h`), little-endian:

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 2 | Преамбула `0x55 0xAA` |
| 2 | 2 | `pkt_size` — размер всего кадра (≤ **256**) |
| 4 | 2 | `pkt_type` |
| 6 | 2 | `seq` — счётчик кадра на канале (ПО инкрементирует в запросах) |
| 8 | `pkt_size−10` | `payload` |
| `pkt_size−2` | 2 | `checksum` — `BSU_Checksum()` по байтам `[0 .. pkt_size−3]` |

### Типы кадров (`pkt_type`)

| Значение | Имя | Направление |
|----------|-----|-------------|
| `0` / `1` | CAN / CAN2 | существующий мост (не лог) |
| **`16`** | **`LOG_REQ`** | ПО → ППКУ |
| **`17`** | **`LOG_RSP`** | ППКУ → ПО (одиночный ответ) |
| **`18`** | **`LOG_DATA`** | ППКУ → ПО (поток данных) |

На UART2: кадры `16…18` обрабатывает **модуль лога**, не `ProtocolParse` CAN.

---

## 3. Команды (`LOG_REQ` payload)

```
[0]     opcode
[1..]   параметры
```

| opcode | Имя | Назначение |
|--------|-----|------------|
| `0x01` | `PING` | проверка связи |
| `0x02` | `GET_INFO` | ёмкость / count / write_head обоих уровней |
| `0x10` | `START_DUMP` | начать потоковую выгрузку лога |
| `0x11` | `STOP_DUMP` | прервать текущую выгрузку |
| `0x12` | `GET_DUMP_STATUS` | статус активной сессии |

Команды записи/стирания **отсутствуют**.

---

## 4. `GET_INFO` (`0x02`)

**Ответ** (`LOG_RSP`, один кадр):

| Смещение | Поле |
|----------|------|
| 0 | `status` (0=OK) |
| 1 | `opcode` эхо |
| 2 | `proto_ver` = 2 |
| 3 | `record_size` = 32 |
| 4..7 | `critical_capacity` u32 |
| 8..11 | `critical_count` u32 |
| 12..15 | `critical_write_head` u32 |
| 16..19 | `general_capacity` u32 |
| 20..23 | `general_count` u32 |
| 24..27 | `general_write_head` u32 |
| 28..31 | `catalog_crc32` u32 |

---

## 5. `START_DUMP` (`0x10`) — выгрузка лога

**Запрос:**

| Смещение | Поле |
|----------|------|
| 1 | `tier`: `0` critical, `1` general, **`2` оба** (сначала critical, затем general) |
| 2..5 | `start_logical` u32 — с какого индекса (0 = с самого старого) |

**Ответ** (`LOG_RSP`):

| Смещение | Поле |
|----------|------|
| 0 | `status` |
| 1 | `opcode` эхо |
| 2..3 | `stream_id` u16 — ID сессии |
| 4..7 | `total_records` u32 — сколько событий будет в потоке |
| 8..11 | `write_head_crit` u32 — снимок на старт |
| 12..15 | `write_head_gen` u32 |

При `status ≠ 0` поток не начинается.  
При `status = 0` ППКУ **сразу после** `LOG_RSP` шлёт серию `LOG_DATA` без ожидания ACK (упрощение v2.0; flow-control — в `STOP_DUMP`).

Если выгрузка уже идёт → `status = BUSY (4)`.

---

## 6. `LOG_DATA` — поток (≤256 байт на кадр)

### 6.1. Заголовок потока в payload

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 2 | `stream_id` |
| 2 | 2 | **`pkt_num`** — номер кадра потока (0, 1, 2…) |
| 4 | 1 | `flags` — см. ниже |
| 5 | 1 | `tier` — уровень записей в этом кадре (`0`/`1`) |
| 6 | 1 | **`rec_count`** — число **полных** событий в кадре |
| 7 | 1 | резерв |
| 8 | 4 | `first_logical` — `logical_index` первой записи в кадре |
| 12 | 4 | `write_head` — снимок уровня на момент сборки кадра |

**`flags`:**

| Бит | Имя | Смысл |
|-----|-----|-------|
| 0 | `FIRST` | первый кадр потока |
| 1 | `LAST` | последний кадр потока |
| 2 | `TIER_CHANGE` | следующий кадр — другой `tier` (при `tier=2` в запросе) |
| 7 | `ERROR` | сбой чтения Flash, поток прерван |

Заголовок потока: **16 байт**.  
Оболочка BSU: **10 байт**.  
Остаётся под события: **256 − 16 − 10 = 230 байт**.

### 6.2. Элемент события в потоке (`LogStreamRecord`)

**37 байт**, всегда целиком:

| Смещение | Поле |
|----------|------|
| 0 | 4 | `logical_index` u32 |
| 4 | 1 | `rec_status`: `0` valid, `1` empty, `2` invalid |
| 5 | 1 | `tier` (эхо) |
| 6 | 31 | `raw[32]` — `EventLogRecord_t` из Flash |

**Максимум событий в одном кадре:** `⌊230 / 37⌋ = 6`.

### 6.3. Алгоритм упаковки (ППКУ)

```
next_logical = start_logical
pkt_num = 0
while есть записи:
    rec_count = 0
    while rec_count < 6
          AND (16 + (rec_count+1)*37 <= 230)
          AND есть next_logical:
        прочитать слот → LogStreamRecord
        rec_count++
        next_logical++
    сформировать LOG_DATA (полные события только)
    pkt_num++
выставить LAST в финальном кадре
```

Неполный хвост кадра **не заполняется** частью события — следующее событие уходит в следующий кадр.  
Допускается padding `0x00` после последнего полного события.

### 6.4. Нумерация и проверка на ПО

1. `pkt_num` строго +1 (после `FIRST` с `pkt_num=0`).
2. `first_logical` + `rec_count` задаёт диапазон индексов в кадре.
3. В каждой записи `logical_index` должен совпадать с ожидаемым.
4. При `tier=2`: сначала все кадры с `tier=0`, затем с `tier=1` (флаг `TIER_CHANGE` на последнем кадре critical).

## 7. `STOP_DUMP` / `GET_DUMP_STATUS`

**`STOP_DUMP` (`0x11`):** прерывает активный поток; ответ `LOG_RSP` с `status=0`.

**`GET_DUMP_STATUS` (`0x12`):** `LOG_RSP`:

| Поле | Описание |
|------|----------|
| `active` u8 | 1 = выгрузка идёт |
| `stream_id` u16 | |
| `pkt_sent` u16 | сколько `LOG_DATA` уже отправлено |
| `records_sent` u32 | сколько событий отдано |

---

## 8. CAN (будущее, не реализуется в v2.0)

Чтение **по одному событию** через сервисные команды CAN (`164…167`, зарезервировано):

- запрос одной записи по `tier` + `logical_index`;
- ответ — **несколько CAN-кадров** (как `GetVersion` 159): фрагменты по 6 байт полезной нагрузки;
- одно событие (32 байта + meta) собирается ПО из серии CAN-ответов.

Потоковая выгрузка «весь лог» по CAN **не планируется** (только RS/UART).

---

## 9. Логический индекс (прошивка)

```
capacity = tier.capacity
count    = tier.valid_count
head     = tier.write_head

oldest = (count < capacity) ? 0 : ((head + 1) % capacity)
physical = (oldest + logical_index) % capacity
```

Классификация `rec_status` — при чтении слота (`valid` / `empty` / `invalid`).

---

## 10. Сценарий ПО (RS485 / UART)

```
1. LOG_REQ PING / GET_INFO
2. LOG_REQ START_DUMP(tier=2, start=0)
3. LOG_RSP → stream_id, total_records
4. Цикл приёма LOG_DATA:
     - проверить pkt_num, flags, rec_count
     - разобрать rec_count × LogStreamRecord
     - valid → парсинг по event_log_catalog.json
5. Кадр с flags.LAST → конец
```

При обрыве: `STOP_DUMP`, повтор `START_DUMP` с `start_logical` = последний полученный + 1.
